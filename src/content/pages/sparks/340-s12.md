# S12 · Party island

**Concept:** Astro islands: `client:` directives, props across the island boundary, and build-time vs browser data.
**Time:** 15–30 minutes in studio, and due before class.

Your Release's interactive part arrives today. Bring a Svelte component you've built (the P3 party builder, the P4 team planner, or the piece your intent brief needs) into `release/` as an island on one page, fed by data the page fetched at build time. Then add view transitions between pages. The work goes in `release/`; this Spark's folder holds only its `NOTES.md`.

## 1. Intent

In `sparks/s12-party-island/NOTES.md` **Intent**: which part of your Release needs to be interactive, and which parts are better as plain HTML? Why?

## 2. Spec: the "done" list

Your Spark is done when:

<!-- done:start -->

- [ ] `release/` has the Svelte integration (`npx astro add svelte`), and `astro.config.mjs` still has no `base`.
- [ ] One page has a Svelte island, with its components in `src/components/`, that works on the live site: every control does something.
- [ ] The page fetches data at build time (in its frontmatter) and passes it to the island as props. Only data crosses: no functions passed from the `.astro` page.
- [ ] The island does something in the browser that needs JavaScript: a lookup by name, or changes to a party or team.
- [ ] The `client:` directive suits where the island sits, and `NOTES.md` says why you chose it over the other two.
- [ ] Everything around the island is plain HTML: with JavaScript off, the page still shows its build-time content and says what the island is for.
- [ ] `<ClientRouter />` is in your layout's `<head>`, and page changes don't animate when Reduce motion is on.
- [ ] Zero warnings in the build and the browser console; the island's accessibility (labels, announced states, focus) is as good as it was in P3 or P4.
- [ ] `sparks/s12-party-island/NOTES.md` covers every section, in your own words.
- [ ] It's committed and pushed, **Build and deploy** is green, and the island works on the live page.

<!-- done:end -->

## 3. Generate

Plan mode first: give Claude the "done" list and point it at the component you're bringing in (its folder in `prototypes/` or `sparks/`). Ask for the integration, then the component copied into `src/components/` and placed with no directive (check it's a dead picture), then the directive, then the props, then `<ClientRouter />`. Read each `★ Insight` about the directive: do you agree?

**Watch for:** no directive (silent dead buttons), `client:load` on everything, a function prop from the page that arrives as `null`, the whole page wrapped into one island, and the island's own `fetch` duplicating what the page already fetched at build time. If you catch one, it's a good entry for "Accepted / changed / rejected."

## 4. Verify

- Click every control on the live page, keyboard only. Does each one do something?
- DevTools → Network, filter "JS": reload and scroll. When does the island's script arrive?
- Turn JavaScript off and reload. What's left, and does it make sense?
- Turn on Reduce motion (macOS: System Settings → Accessibility → Display) and move between pages.

## 5. Explain

Finish `NOTES.md`. Name your directive and the two you didn't choose, with a reason for each, and one piece of data you moved from the browser to build time (or the other way) and why. [`/dig-deeper`](/340/skills/dig-deeper/) on hydration is a good dig-deeper starting point.

Then run [`/check`](/340/skills/check/) `sparks/s12-party-island` and paste in the "done" list above (the **Copy** button copies it).
