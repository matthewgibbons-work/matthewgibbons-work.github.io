# S13 · Practice site tests

## The problem

Your practice site works today. Next week you'll change the layout, rename a component, or let Claude "tidy" something, and **one of these will quietly break**: the island's label disappears, the nav stops marking the current page, a new colour fails contrast. **Right now** the only check is you, by hand, when you remember, and a test you've never seen fail might not be checking anything at all.

Your job is the "Wanted" column, on your practice site: Playwright tests that people can do the main thing with the keyboard, the nav says where they are, and axe finds nothing on any kind of page, and each test can fail. Plan on 15–30 minutes after the kit update. It's due before class on Wed Dec 9 and graded Complete / Not yet straight from your repo, so there's nothing to submit. Do the Dec 7 kit update first (step 0).

The tests go in `sparks/astro-practice/`; this Spark's folder holds only its `NOTES.md`. After the kit update, they run on GitHub on every push. Claude is on the **Explanatory** output style: read its `★ Insight`s, and decide. The step most people miss is breaking each test once on purpose: a test that has never gone red hasn't proved anything.

## 0. The kit update (do this first)

In your `dight340` session, run [`/update-kit`](/340/skills/update-kit/). Before it changes anything it tells you what it will do. If it asks about a file you changed, choose **show me the difference**, then decide.

GitHub Desktop should show two changed files, `.course-kit-version` and `.github/workflows/check.yml` (it now runs Playwright too). Commit "Update course kit for Dec 7" and push.

## 1. Intent

Create `sparks/s13-practice-tests/` with its own `NOTES.md`. In its **Intent**: what's the one thing a visitor must be able to do on your practice site (your S12 island is a good candidate), and what would it cost them if it broke?

**Predict before you prompt.** Under your intent, add a line that starts `Prediction:`. Which thing on your site do you expect axe to flag first if you broke it, and which breakage would *only* your keyboard test catch? A guess is fine; you'll check it in step 5.

## 2. Spec: the "done" list

Your Spark is done when:

## 3. Generate

Plan mode first: give Claude your intent and the "done" list (not your prediction: that's for you), and ask for a test plan (what each test proves) before any code. Approve the `npm install` only for the two packages above. Then `npx playwright install chromium` once. Write or generate the tests one at a time, and run each before the next.

**Watch for:** CSS selectors instead of roles, `waitForTimeout` instead of waiting for the island, axe rules switched off to get a pass, a test that only checks the page loaded, and no `webServer` in the config. If you catch one, it's a good entry for "Accepted / changed / rejected."

## 4. Verify

Walk the sketch's five rows on your own site:

- `npx playwright test`, then break one thing per test and run again. Does the right test fail, with a message you can understand?
- `npx playwright test --repeat-each 10` on the island test. Ten passes?
- After you push: **Actions** → **Checks** → the Playwright step. Green? If not, read which test and which axe rule.
- Do your main task yourself with VoiceOver (Cmd+F5). Anything the tests didn't notice?

## 5. Explain

**Check your prediction.** Under your `Prediction:` line, add `What it used:`: what axe actually flagged and what only the keyboard test caught, where your guess matched, where it didn't, and why.

Then finish `NOTES.md`. Include one locator read aloud as a screen reader would announce it, and what axe can't check on your site. [`/dig-deeper`](/340/skills/dig-deeper/) on why Playwright recommends `getByRole` is a good dig-deeper starting point.

Then run [`/check`](/340/skills/check/) `sparks/s13-practice-tests` and paste in the "done" list above (the **Copy** button copies it).
