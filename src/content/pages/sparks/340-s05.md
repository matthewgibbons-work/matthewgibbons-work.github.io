# S05 · Party modules

Split your S02 party page into a Vite project: the party's rules (no seventh Pokémon, no duplicates, whatever yours needs) in a module with Vitest tests, and a page that imports them. Plan on 15–30 minutes after the kit update. It's due before class on Wed Nov 4 and graded Complete / Not yet straight from your repo, so there's nothing to submit. If you didn't finish the Nov 2 kit update in class, do that first (step 0).

From here on, every push runs the course's **feedback checks** (ESLint and your tests) on GitHub; they report, they never block. Claude is still on the **Learning** output style, so write any `TODO(human)` yourself; a test is a good one to write by hand. The step most people miss is `base: './'` in `vite.config.js`: without it the dev server works and the live page is blank.

## 0. The kit update (if you didn't finish it in class)

Download [`dight340-update-nov02.zip`](/downloads/dight340-update-nov02.zip) and double-click it, so it unzips into Downloads. In your `dight340` session, paste:

```text
My instructor asked me to update the course kit. Copy everything in ~/Downloads/dight340-update-nov02/ into the root of this repo, replacing what's there, including the hidden .claude, .github, and .gitignore. Then show me git status.
```

Check the Changes tab in GitHub Desktop (new: `eslint.config.mjs`, `.github/workflows/check.yml`, `.claude/hooks/`; changed: `AGENTS.md`, `.claude/settings.json`, `.gitignore`), commit "Update course kit for Nov 2", and push. Then open a **new** session, so Claude Code loads the hook.

## 3. Generate

Plan mode first: give Claude your intent and the "done" list, and agree on the plan before it writes code. Ask for the project setup first, then `party.js` and its tests, then the page. Run the tests yourself between steps (`npx vitest run` in the Spark's folder, or ask Claude to). When it proposes `npm install`, read the package names before you agree: they should be `vite` and `vitest`, nothing else.

**Watch for:** a project template you didn't ask for (React or TypeScript; the scope guard stops React, but not TypeScript), no `base: './'`, the template's leftover counter and logos, tests that pass even when the rule is broken, and `party.js` reaching into the page. If you catch one, it's a good entry for "Accepted / changed / rejected."

## 4. Verify

- In the Spark's folder, `npm run dev`: open the `localhost` address. Does the party work with the keyboard, with a clean console?
- Change the rule in `party.js` (6 to 7, say) and run `npx vitest run`. Red? Put it back. Green?
- `npm run build`, then `npm run preview`: does the built page work too? Open `dist/index.html` in a text editor: do the paths start with `./`?
- Push, then open your repo on GitHub → **Actions** → the latest **Checks** run. What did ESLint and Vitest say?

## 5. Explain

Finish `NOTES.md`. Include which test you'd trust least and why, what the Checks run reported, and what you wrote for any `TODO(human)`. [`/dig-deeper`](/340/skills/dig-deeper/) on what `package-lock.json` is for, or on `export` vs `export default`, is a good dig-deeper starting point.

Then run [`/check`](/340/skills/check/) `sparks/s05-party-modules` and paste in the "done" list above (the **Copy** button copies it).
