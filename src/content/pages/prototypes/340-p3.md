# P3 · Party builder

**Units:** Svelte logic and events (Mon Nov 9). There's no class on Wed Nov 11, so this week is one unit and a longer studio. No late penalty; rework is welcome until Dec 9.

## The brief

Build a party builder in Svelte. A trainer looks Pokémon up by name and adds them to a party of up to six, removes them, and filters the party by type ("show me only my water types"). Everything you've done since S02 comes together here, but now Svelte's blocks carry the logic: `{#each}` with a key for the party, `{#if}` for empty and full, and `{#await}` (or one clear status variable) for each lookup.

Two rules make it a party: no more than six, and no duplicates. Put them in a plain module with Vitest tests, as in P2, so you know they hold.

Own-choice option: another free, no-key JSON API where building a small collection makes sense, by proposal to the instructor first.

## Spec: the "done" list

**Data and logic**

- [ ] `prototypes/p03-party-builder/` is a Svelte 5 + Vite project in JavaScript, with `base: './'` and no template leftovers.
- [ ] A labeled form looks a Pokémon up by name (`onsubmit`, `fetch`, a `response.ok` check). A misspelled name gives a clear message on the page.
- [ ] The party rules (at most six, no duplicates) live in a plain module with Vitest tests, and the page uses them. When a rule stops an add, the page says why.
- [ ] A type filter (buttons, a `<select>`, or radio buttons, all labeled) shows only the party members of that type, with an "all types" option. The filter is a `$derived` value, not a second copy of the party.

**Svelte blocks**

- [ ] The party uses a **keyed** `{#each}`, with an `{:else}` (or `{#if}`) for an empty party, and a different message when the filter matches no one.
- [ ] Loading and error states for each lookup come from `{#await}` or a single status value, not three flags that can disagree.
- [ ] Zero `a11y_` warnings, and no other warnings, in the terminal running `npm run dev`.

**States people can perceive**

- [ ] Loading, added, removed, "party full", and error messages are announced (an `aria-live` region that's on the page from the start).
- [ ] After a remove, focus goes somewhere sensible. The add button can't be pressed twice while a lookup is in flight.

**Every Prototype**

- [ ] `const`/`let` and `===` only. No console errors. The **Checks** run is green.
- [ ] Works with the keyboard alone. Focus stays visible.
- [ ] Readable at 200% zoom (Cmd/Ctrl +): nothing cut off, overlapping, or hidden.
- [ ] Linked from your hub under Prototypes. The **Build and deploy** run is green and the live page loads.

## Working in the loop

1. **Intent:** who builds parties, and what do they need to see while they do? Write it in `NOTES.md` first.
2. **Spec:** start from the list above.
3. **Generate:** plan mode first, then small steps: the project, the rules module and its tests (break one on purpose), a hard-coded party with remove and filter, then the lookup form. Under the Learning style, Claude will leave `TODO(human)`s; the "party full" message or the filter's `$derived` are likely. Write those yourself.
4. **Verify:** keep the `npm run dev` terminal visible for warnings; add seven, add a duplicate, misspell one, filter to a type nobody has, remove everyone with the keyboard; throttle to Slow 4G and double-press Add; zoom to 200%; check both runs in **Actions**.
5. **Explain:** finish `NOTES.md`, then run [`/check`](/340/skills/check/) `prototypes/p03-party-builder` and paste in the "done" list (the **Copy** button copies it).

**Watch for:** an unkeyed `{#each}`, a filter that copies the party into a second `$state` (and drifts from it), clickable `<div>`s for type chips, a type shown only as a colour, and rules written inside the component where the tests can't reach them.
